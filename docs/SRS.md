# Software Requirements Specification (SRS)

## 1. Introduction

### 1.1 Purpose
The purpose of this document is to define the software requirements for a custom Point of Sale (POS), Inventory Management, and Financial Ledger system designed specifically for a solo-operated micro-retailer operating in a low-income, labor-constrained market. 

### 1.2 Document Conventions
* **RBAC:** Role-Based Access Control.
* **POS:** Point of Sale.
* **Tingi:** Bulk-breaking repackaging model.
* **LAN:** Local Area Network.
* **WAN-Resilient:** The system prioritizes local network operations but leverages Wide Area Network (Internet) connections for non-critical background tasks.
* **Container Registry:** A centralized repository (e.g., Docker Hub) for storing and distributing Docker images.

### 1.3 Intended Audience and Reading Suggestions
This document is intended for the primary stakeholder (Admin/Owner) and software developers. Developers must use this document in strict conjunction with the accompanying Software Design Document (SDD) to guide the Django and PostgreSQL implementation.

### 1.4 Product Scope
The software facilitates daily retail operations, automated inventory management, and strict financial control. It handles unique workflows, such as solution-based meal bundling, bulk-breaking arbitrage ("Tingi"), and a localized informal credit system. The system operates on a "WAN-resilient" architecture: core retail operations function entirely over the local LAN, while background tasks leverage the host machine's internet connection.

## 2. Overall Description

### 2.1 Product Perspective
This system is a standalone web application containerized via Docker. It replaces a manual, "zero-tech" ledger approach with a localized digital solution, operating on a LAN utilizing a PostgreSQL database and Django ORM to ensure strict data integrity, atomic state management, and multi-device concurrency. 

### 2.2 Product Functions
* **Transaction Processing:** Standard checkout, frontend cart state management via PostgreSQL draft records, high-margin service fee processing, and loyalty tracking.
* **Inventory Tracking:** Real-time deduction of parent/child composite items utilizing Django atomic database-level transactions, CSV data seeding, and automated 10-day sales velocity bucketing.
* **Financial Management:** Integrated cashbook tightly coupled to transaction line items, plus strict, capped credit ledger management.
* **Maintenance & Disaster Recovery:** Over-The-Air (OTA) schema migrations deployed via a secure container registry, and automated cloud backups.

### 2.3 User Classes and Characteristics
* **Admin/Owner:** Requires full visibility and configuration access across all system parameters, reporting, error correction, and equity management.
* **Manager:** Full operational capabilities (including custom credit limit approvals) but restricted from altering core system configurations or correcting ledger errors.
* **Cashier/Clerk:** Entry-level staff member focused entirely on processing checkout transactions. Experiences hard stops on unauthorized credit sales.
* **Customer:** Tracked in the database via an extended profile for loyalty tracking, metrics, and credit ledger mapping.

### 2.4 Operating Environment
* **Server:** Local host machine (e.g., mini-PC or dedicated laptop) running Docker/Docker Compose. Must have a fresh CMOS battery installed prior to deployment.
* **Network:** The host machine maintains an active internet connection for maintenance/backups, but the POS application is architected to be completely WAN-independent for all daily retail operations over the LAN.
* **Client:** Responsive modern web browser on standard POS hardware, tablets, or mobile devices connected to the LAN.

### 2.5 Design and Implementation Constraints
* The system must utilize Django (Python) for web routing, business logic, framework structures, database modeling, and ORM operations, alongside PostgreSQL for storage.
* Dependency management must be handled by Astral `uv`.
* Celery and Redis are strictly prohibited to prevent container bloat.

## 3. External Interface Requirements

### 3.1 User Interfaces
* **Dashboard:** A centralized Admin view displaying Daily Sales, Weekly Gross Profit, Total Outstanding Debt, Low-Stock Warnings, Top Items, Top Customers, and Sales by Clerk.
* **Quick Service Grid:** A POS tab featuring one-tap buttons for ringing up 100% margin services (e.g., microwave heating).
* **Offline Recovery Grid:** A rapid-entry spreadsheet grid for digitizing offline receipt books without corrupting reporting timestamps.

### 3.2 Hardware Interfaces
* **Barcode Scanners:** The POS interface must actively listen for strict, hidden keystroke envelopes (e.g., F12 before, ENTER after) generated by physical scanners to guarantee payload capture regardless of active UI focus.
* **Network Printers & Cash Drawers:** To ensure cross-device compatibility (tablets and PCs), thermal receipt printers must be Network/IP-based (not USB). The electronic cash drawer must connect to the IP printer via RJ11, allowing any LAN device to send a unified print/kick command.

## 4. System Features

### 4.1 POS Checkout & Cart State Management
* **4.1.1 Description:** The core transaction engine optimized for speed and data resilience.
* **4.1.2 Functional Requirements:**
    * **State Management:** The active POS cart must not rely on volatile frontend memory. Every barcode scan must instantly execute an HTMX request that writes directly to a temporary `Transaction` database row with a "Draft" status.
    * **Line Item Normalization:** The system must break down all completed sales into normalized `TransactionLineItem` records.

### 4.2 Dynamic Inventory Architecture
* **4.2.1 Description:** An inventory schema accurately tracking raw goods packaged as bundles or micro-portions.
* **4.2.2 Functional Requirements:**
    * The system shall support composite items via an explicitly defined Many-to-Many "Through Table" in Django.
    * **Concurrency Control:** Scanning a composite item at checkout shall deduct parent components within a Django `transaction.atomic()` block, using database-level row locking via `.select_for_update()` and `F()` expressions to prevent race conditions.
    * **Data Seeding:** The system must include a robust data ingestion command utilizing Django's `bulk_create()` for rapid bulk CSV ingestion of the initial 1,000+ SKUs.

### 4.3 The "Black Book" Credit Ledger
* **4.3.1 Description:** A strict, capped informal credit management tool linked directly to Customer profiles.
* **4.3.2 Functional Requirements:**
    * The system shall apply configurable global/custom dollar limits and settlement periods.
    * **Empathetic UI:** When enforcing a hard checkout stop due to exceeded limits, the UI must present clear, de-escalating error messaging using Alpine.js conditional visibility state management.
    * The system shall include an "Equity Offset" feature allowing the Admin to clear personal credit balances by logging out-of-pocket inventory purchases.

### 4.4 Integrated Cashbook Module
* **4.4.1 Description:** A unified, immutable ledger tracking inflows/outflows to calculate exact physical drawer cash.
* **4.4.2 Functional Requirements:**
    * **Transaction Coupling:** Every completed sale must simultaneously write a positive entry to the Cashbook utilizing an atomic Django database transaction.
    * **Immutability & Auditability:** All outgoing till expenses must record the ID of the user submitting the entry. Entries cannot be edited or hard-deleted; errors may only be countered with an opposing correction entry by an Admin.

### 4.5 Digital Loyalty Program
* **4.5.1 Description:** An automated alternative to physical punch cards.
* **4.5.2 Functional Requirements:**
    * **Feature Toggle:** This feature must be disabled by default and configurable (enable/disable) by Admin or Manager roles.
    * **Trigger Math:** When enabled, customers earn exactly 1 point for every 1.00 spent on completed *non-credit* transactions. 
    * **Alert Threshold:** The POS UI shall automatically trigger an alert to the cashier when a customer's profile reaches 100 points, indicating a reward is available.

### 4.6 Offline Recovery Mode
* **4.6.1 Description:** A bulk-entry interface for digitizing power-outage receipts.
* **4.6.2 Functional Requirements:**
    * **Temporal Separation:** The database must explicitly separate user-inputted historical transaction timestamps from the immutable system creation timestamp to protect reporting integrity.

## 5. Other Nonfunctional Requirements

### 5.1 Performance & Precision Requirements
* **Financial Precision:** All currency and fractional inventory fields must utilize strict database Decimal structures (`DecimalField` in Django). Floating-point types are strictly prohibited.

### 5.2 Data Integrity Requirements
* **Immutability Constraint:** All financial, inventory, and ledger relationships must utilize strict programmatic or database-level constraints (`on_delete=models.RESTRICT`) to protect ledger history.

### 5.3 Deployment & Maintenance
* **Cloud Disaster Recovery:** Automated PostgreSQL snapshot backups must be securely pushed to a cloud storage bucket leveraging the host machine's internet connection.
* **Registry-Based Pipeline:** Software updates must be applied by executing a `docker compose pull` from a Container Registry.
* **Admin Bootstrapping:** The initial deployment must execute a script or consume environment variables to automatically provision the primary Admin account so the owner is not locked out on Day 1.
